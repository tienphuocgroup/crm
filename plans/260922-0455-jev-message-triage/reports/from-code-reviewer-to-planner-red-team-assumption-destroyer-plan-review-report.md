## Finding 1: Retry semantics are self-contradictory and the "within the lease" claim is false

- **Severity:** Critical
- **Location:** Phase 2, "Implementation Steps" step 7; plan.md "Acceptance criteria" bullet 4; Phase 2 "Success Criteria" "429/529 retry inside the lease"
- **Flaw:** Step 7 says on non-terminal `ok: false` "throw so the lease retries", and in the same sentence says "The whole body sits in one try/catch that returns `SENTENCES.internal` and bumps `jevError`, matching `runMessageSend`". The outer catch swallows the throw. `completeTask` then finishes the task with "internal". Nothing retries. If the throw escapes instead, the direct lane does not retry inside the lease: `runDirect` catches the rejection, `reconcileDirect` calls `settle()`, which only writes enrichment status on a contact or company and returns early when the task has neither. The task stays leased for `VISIBLE_LEASE_MS` (6 minutes), is re-claimed after expiry, and `attempts` is incremented at claim. `MAX_ATTEMPTS = 3`, then `retireExhausted` finishes it with "Gave up after 3 attempts: the session never reported back."
- **Failure scenario:** Jev returns 429 twice (client backoff exhausted). Handler throws. Option A (outer catch as written): task completes as "internal", `triagedAt` stays null, the message is never triaged. Option B (throw escapes): message waits 6 minutes per attempt, gets 3 attempts total, then is retired with a misleading outcome sentence about a session. A 30-minute vendor outage leaves every message from that window untriaged forever.
- **Evidence:** `apps/agent/agent/lib/messaging/message-send.ts:249-304` (outer `try` … `catch (error) { messagingError(...); return SENTENCES.internal }`); `apps/agent/agent/lib/dispatch.ts:75-97` (`runDirect` maps rejection to `{ finished: false, reason }`), `:100-105` (`reconcileDirect` → `settle(task, FAILED, reason)`); `apps/agent/agent/lib/enrichment.ts` `settle` → `write` → `if (!subject.contactId && !subject.companyId) return;`; `apps/agent/agent/lib/tasks.ts:45-55` (`attempts + 1` on claim, `attempts < MAX_ATTEMPTS`), `:73-85` (`retireExhausted`); `packages/db/src/agent-tasks.ts:38,40`; `apps/agent/agent/lib/dispatch-config.ts:7` (`leaseMs: 6 * MINUTE_MS`). Plan quote: "on `ok: false` with `terminal` stamp `triagedAt` and return `SENTENCES.rejected`, else throw so the lease retries … The whole body sits in one try/catch that returns `SENTENCES.internal`."
- **Suggested fix:** Pick one model and write it down. Recommended: never throw. On transient failure return a sentence, leave `triagedAt` null, and re-queue explicitly with `scheduleTask({ kind: "message-triage", dueAt: now + backoff, payload })` (pattern: `tasks.ts:138`), bounded by an attempt counter in the payload. Rewrite acceptance criterion 4 to state the real retry cadence and cap.

## Finding 2: "A later key triages the backlog" has no mechanism

## Finding 3: The writer does not queue inside the transaction, and queueing inside one drops the poke

- **Severity:** High
- **Location:** Phase 2, "Related Code Files" (writer entry), "Implementation Steps" step 5 and 6, "Architecture" diagram
- **Flaw:** The plan says the profile task is queued "inside the same transaction path" and asks to extend `withTasks` so "the writer can call it inside its transaction". Neither is true of `store()`. `store()` opens `this.db.$transaction` directly and queues the profile task after commit via `this.agent.messageIdentityProfileRequested(identity.id)` with no client. `withTasks` is used by `messaging.service.ts` for outbound sends, not by `store()`. If the implementer instead passes `tx` into `enqueue()`, `enqueue()` skips `this.poke()` when a client is present, so the task waits for the next scheduled dispatch tick instead of being poked. If the implementer copies the profile path (queue after commit), a crash between commit and queue loses the task permanently, because dedup is by pending task and the writer never re-queues.
- **Failure scenario:** Implementer follows the plan literally, extends `AgentTaskQueue`, and passes `tx`. Triage tasks are created but no poke fires. "Within one dispatch tick" now means "whenever the schedule next runs", which the plan does not quantify. Alternatively, API process restarts after commit but before `messageTriageRequested` resolves; that message never gets a task.
- **Evidence:** `apps/api/src/messaging/messaging-writer.service.ts:102` (`this.db.$transaction(async (tx) =>`), `:236-249` (transaction returns, then `await this.requestProfile(identity)` at `:247`), `:613-618` (`requestProfile` calls `this.agent.messageIdentityProfileRequested(identity.id)` with no client); `apps/api/src/agent/agent-trigger.service.ts:143-148` (optional `client`), `:515-521` (`if (!client) this.poke();`); `withTasks` callers: `agent-definitions.service.ts:329`, `messaging.service.ts:136` only. Plan quote: "queue after the insert, inside the same transaction path as the profile task" and "Extend the `withTasks` queue interface so the writer can call it inside its transaction."
- **Suggested fix:** Decide explicitly: pass `tx` into `messageTriageRequested(messageId, tx)` inside the `$transaction` callback, and call `this.agent.poke()` (or a public wrapper) after the transaction commits when a task was created. Drop the `AgentTaskQueue` extension unless `queueOutbound` also needs it. Add a writer spec case for "task row exists after commit".

## Finding 4: Switching `createMany` to `create` inside the interactive transaction changes duplicate behaviour

- **Severity:** High
- **Location:** Phase 2, "Implementation Steps" step 6
- **Flaw:** A `create` that hits the `[threadId, externalId]` unique raises P2002 inside the open Postgres transaction. Postgres marks the transaction aborted. The plan's "keeping the duplicate branch" needs a try/catch inside the callback; every statement before it (`lastInboundAt` update on the identity, the thread upsert) is rolled back instead of committed as today. The plan does not name this behaviour change or a test for it.
- **Failure scenario:** Zalo redelivers a webhook. Today: `createMany` returns `count: 0`, the thread upsert and identity `lastInboundAt` bump commit, `store()` returns `duplicate`. After the change: P2002, aborted transaction, all writes rolled back, and Prisma's error path may log the failure as an error on every redelivery.
- **Evidence:** `apps/api/src/messaging/messaging-writer.service.ts:110-119` (identity `lastInboundAt` updateMany), `:127-149` (thread upsert), `:152-173` (`createMany` + `skipDuplicates`, `count === 0` branch); `packages/db/prisma/schema.prisma:1664` (`@@unique([threadId, externalId])`); `messaging.service.ts:~340` already has a P2002 helper that the plan does not reference. Plan quote: "switch the insert to `create` with `select: { id }` guarded by the existing unique on `[threadId, externalId]`, keeping the duplicate branch".
- **Suggested fix:** Keep `createMany`. When `inserted.count === 1`, run `tx.message.findUniqueOrThrow({ where: { threadId_externalId: { threadId: thread.id, externalId: incoming.externalId } }, select: { id: true } })`. `incoming.externalId` is a non-null `string` (writer `:49`), so the compound key is always addressable. No error path, no behaviour change on duplicates.

## Finding 5: Urgency sort puts untriaged threads first and breaks cursor pagination

- **Severity:** High
- **Location:** Phase 3, "Architecture" orderBy line; "Implementation Steps" step 3; Phase 2 schema `@@index([lastUrgency, lastMessageAt])`
- **Flaw:** (a) Postgres `ORDER BY lastUrgency DESC` places NULL first. Every thread with no verdict (below threshold, sticker, not yet triaged) sorts above level 3. (b) The plan's orderBy drops the `{ id: "desc" }` tiebreaker that the current query relies on for `cursor: { id }` pagination. Ties on `(lastUrgency, lastMessageAt)` produce non-deterministic page boundaries.
- **Failure scenario:** Rep clicks "urgency". Top of the list is every untriaged thread. Level 3 complaints are below the fold. Rep scrolls; page 2 repeats or skips threads that tie on urgency and timestamp.
- **Evidence:** `apps/api/src/messaging/messaging.service.ts:183-187` (`cursor: { id: input.cursor }, skip: 1`, `orderBy: [{ lastMessageAt: "desc" }, { id: "desc" }]`); repo precedent for nulls handling: `apps/api/src/contacts/contacts.service.ts:110` and `apps/api/src/deals/deals.service.ts:93` use `{ sort: dir, nulls: "last" }`. Plan quote: "orderBy sort === "urgency" ? [{ lastUrgency: "desc" }, { lastMessageAt: "desc" }] : [{ lastMessageAt: "desc" }]".
- **Suggested fix:** `[{ lastUrgency: { sort: "desc", nulls: "last" } }, { lastMessageAt: "desc" }, { id: "desc" }]`. Add an API test with one null-urgency thread and one level-3 thread. Keep `{ id: "desc" }` on both sort branches.

## Finding 9: Thread `lastIntent`/`lastUrgency` write races under the direct lane's concurrency

- **Severity:** Medium
- **Location:** Phase 2, "Architecture" ("when this is the newest inbound"); "Implementation Steps" step 7; Success criterion "follow the newest inbound message only"
- **Flaw:** The direct lane runs six tasks at once. Two inbound messages from the same thread queued seconds apart can be triaged concurrently. Each handler reads "am I the newest inbound", both see yes or the older one reads before the newer commits, and the older verdict lands last. The plan's test (h) covers sequential order only.
- **Failure scenario:** Customer sends "giá bao nhiêu?" then "KHẨN CẤP, con tôi đang sốt". Both tasks run in the same batch. The pricing verdict writes after the urgent one. Thread shows `lastIntent = PRICING`, `lastUrgency = 0`, and sorts to the bottom of the urgency view.
- **Evidence:** `apps/agent/agent/lib/dispatch-config.ts:6` (`concurrency: 6`), `apps/agent/agent/lib/dispatch.ts:53-63` (`runLimited(VISIBLE_CONCURRENCY, …)`); writer precedent for monotonic guarded writes: `messaging-writer.service.ts:184-194` (`updateMany` with `lastMessageAt: { lt: incoming.sentAt }`). Plan quote: "update MessageThread (lastIntent, lastUrgency) when this is the newest inbound".
- **Suggested fix:** Write the thread with a guarded `updateMany({ where: { id: threadId, lastInboundAt: { lte: message.sentAt } }, data: { lastIntent, lastUrgency } })`. No read-then-write. Add a test that triages two messages out of order and asserts the newer wins.
