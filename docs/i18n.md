# i18n — read before touching any user-visible string

English is the only shipped locale, and every user-visible string in `apps/app`
and `packages/ui` still goes through a catalog. That is deliberate: the catalog,
checker and pseudo-locale were built in one pass so that adding Vietnamese later
is a translation job, not a refactor.

## Locale resolution

- **The `NEXT_LOCALE` cookie is a cache; the `user.locale` column is truth.**
  `apps/app/i18n/resolve-locale.ts` reads the cookie on every request and falls
  back to `en`. The DB column exists so a new browser gets the same language —
  `LocaleReconciler` in `apps/app/app/(app)/[slug]/layout.tsx` re-seeds a
  missing cookie from the row. When they disagree, the DB wins on the next
  signed-in load.
- **The cookie name is written once**, `LOCALE_COOKIE` in `apps/app/i18n/locale.ts`.
  Import it; a second spelling is a silent failure, because an unmatched cookie
  just means "default locale" and nothing throws.
- **`i18n/locale.ts` must stay importable from client code** — no `next/headers`
  in it. The server-only read lives in `i18n/resolve-locale.ts`. Merging them
  once broke the client bundle at build.
- **There is no URL locale segment, no middleware, no link rewriting.** Decided
  in the round-1 plan and not reopened casually: the app is a single-tenant tool
  behind a sign-in, not an SEO surface.
- `users.setLocale` is the one mutation; the settings switcher writes the cookie
  optimistically, then the row, then `router.refresh()`. The cookie is
  deliberately not `httpOnly` — the client writes it for instant feedback, and a
  UI language is not a secret.

## cacheComponents and the Suspense boundary

`cacheComponents: true` is still on, and the cookie read is request-time data.
**Any component that resolves the locale — directly or through
`getTranslations` — must sit inside a `Suspense` boundary.** The root layout
mounts `LocaleProvider` inside one; `LocalDateTimeHydrator` has its own. Mount a
locale read above every boundary and the build fails on every prerendered route
with "encountered runtime data during prerendering" — that is the guard working,
not a flake. The cost already paid: `/` serves a static shell and streams the
translated tree. Re-enabling full static prerender of translated content would
need `next/root-params` and a URL segment — a future round's problem, recorded
here so nobody trades it away by accident.

## Catalogs and namespaces

`apps/app/messages/en/<namespace>.json`, merged in `apps/app/i18n/request.ts`.
The namespaces are fixed: `common`, `nav`, `settings`, `deals`, `companies`,
`contacts`, `dashboard`, `landing`, `agent-panel`, `ui`. Do not invent one — the
extraction convention (`.agents/skills/i18n-extract/`) keys everything to this
list, and `ui` is not a next-intl namespace at all but the override feed for
`packages/ui` (below).

Keys are `<namespace>.<area><Thing>` camelCase, named for meaning, not location.
Shared strings live in `common` only when the English **and the meaning** are
identical everywhere — `Save` on two unrelated forms translates identically,
"moved." on a contact and on a deal does not. When unsure, duplicate; a wrong
merge is harder to unpick than a duplicate is to delete. Interpolation is ICU
named placeholders, markup goes through `t.rich`, plurals through ICU `plural` —
never concatenation, which is how `formatCount` died: `count + " deals"` cannot
survive translation, so it became per-namespace ICU messages.

## Server, client, pure function

The full decision rule with worked examples is
`.agents/skills/i18n-extract/SKILL.md`. The short form:

- `"use client"` file → `useTranslations("ns")`.
- Server component → `await getTranslations("ns")`.
- Neither — a pure helper in `apps/app/lib/` — **returns a key, never a
  sentence**, and the render site translates. Threading `t` into a pure helper
  makes it untestable without a provider. The tests assert keys; a test that
  imports `messages/en/*.json` to re-assert English has recreated the coupling
  the refactor removed, and that is why none does.

## packages/ui: UiStringsProvider, never next-intl

`packages/ui` renders its own strings from `DEFAULT_UI_STRINGS`
(`packages/ui/src/lib/ui-strings.ts`), overridable once at the root through
`UiStringsProvider`. The app feeds it the `ui` namespace in
`apps/app/components/locale-provider.tsx`. **No next-intl import may enter
`packages/ui`, direct or transitive** — the package renders correctly with no
provider at all, which is what keeps it buildable and testable outside the app.
`messages/en/ui.json` mirrors `DEFAULT_UI_STRINGS` key-for-key; an orphan on
either side means someone edited one and not the other.

Formatting is locale-aware but defaulted: `formatDay`, `formatMoney`,
`formatMoneyCompact`, `formatPercent` take a trailing locale defaulting to
`en-US`, and components read the active one from `useUiLocale()`. Two things are
deliberate here. `fractionDigits` stays pinned to `en-US` — it resolves how many
decimals a *currency* has, not how it displays, and changing it changes rounding
(`docs/currency.md`). And the old `Intl.NumberFormat(undefined, …)` calls are
gone because `undefined` meant server locale on the server and browser locale in
the browser — money could render differently before and after hydration.

The one surface that cannot use React at all is
`apps/app/components/local-date-time.tsx`: its relative-time strings run inside
a stringified DOM script. `buildLocalDateTimeScript(locale, labels)`
(`apps/app/lib/local-date-time-script.ts`) interpolates catalog labels into the
blob, escaping `<` as `\u003c` so a catalog value containing `</script>` cannot
terminate the tag. The TS fallback reads the same labels — they must stay
byte-identical or the text visibly flips at hydration.

## The checker, the allowlist, the ratchet

`bun run i18n:check` (`apps/app/scripts/i18n/`) parses every `apps/app` and
`packages/ui` source file with the TypeScript compiler and flags JSX text, JSX
expression literals, `placeholder`/`title`/`aria-label`/`alt` attributes, and
literal `toast.*()` arguments. It runs in CI after `lint` and fails the build on
any finding. AST, not grep — grep cannot tell `<div>Save</div>` from
`className="Save"`.

- **`allowlist.json`** is for genuinely untranslatable text — brands, vendor
  names, ISO codes, wire values like the `x-crm-*` headers. Every entry carries
  a `reason`. Matching is exact, not substring, so `Comp AI` cannot silently
  exempt a sentence that mentions the brand. It is not a way to make an
  inconvenient finding disappear.
- **`ratchet.json`** is the not-yet-migrated list. It is `[]` and must stay
  `[]` — adding a path is a reviewable diff, which is the point.
- What the checker cannot see: object literals (`metadata`, label maps,
  column definitions) and strings inside string blobs. The pseudo-locale is the
  independent second net for those; the extraction skill also says to grep for
  `export const metadata` explicitly.
- `toast.error(error.message)` is not a finding: API prose stays English by
  design this round, surfaced verbatim.

## Pseudo-locale

`bun run i18n:pseudo` accents every `en` catalog into `messages/pseudo/`
(gitignored, generated on demand), preserving ICU placeholders and tags. In dev,
set `NEXT_LOCALE=pseudo` and walk the app: **any unaccented glyph outside the
allowlist is a missed string** — that is the whole test, and it catches exactly
the class the AST rules cannot. The locale only resolves when
`NODE_ENV !== "production"`; `SUPPORTED_LOCALES` stays `["en"]` and production
falls back to `en`.

## Adding a language

Round 2, expected to need zero code changes beyond these:

1. `messages/vi/<namespace>.json` for all ten namespaces, translated from `en`.
2. Add `"vi"` to `SUPPORTED_LOCALES` in `apps/app/i18n/locale.ts` and to the
   `users.setLocale` zod enum in `apps/api/src/users/users.contracts.ts`
   (regenerate the router type), and a label in the settings switcher.
3. Teach `i18n/request.ts` to load the new locale (the pseudo branch already
   shows the dynamic-import shape) and `intlLocale()` the BCP47 mapping.
4. Walk the pseudo-locale first, then the new language.

Do not create a partial `messages/vi/` ahead of the translation being complete —
a half-filled catalog ships mixed-language screens.

## Syncing from upstream

The repo is a fork; upstream copy edits arrive only via a deliberate
`git merge upstream/release`. After any sync: run `bun run i18n:check` — new
upstream literals fail it; run the `i18n-extract` skill on the flagged files;
then diff the `messages/en/**` values against the literals the merge removed, so
an upstream copy edit updates the catalog instead of forking from it.

## Decisions this round, so they are not re-litigated

- `TYPE_LABELS` (`packages/db/src/fields-shape.ts`) moved to the catalog keyed
  by enum — the fields UI renders them, so they are user-visible copy.
  `packages/db` keeps no i18n dependency.
- Standard field names in `components/crm/fields/standard-fields.ts` are
  extracted (`common.fields.standard*`): they describe hardcoded Prisma columns,
  have no rename mechanism, and never round-trip through the DB — product copy,
  not user data. The user-data rule covers `FieldDefinition.label` and
  `FieldOption.label`, which render as stored and are never translated.
- `<html lang>` is static `en` this round — it sits above the root Suspense
  boundary, and the switcher patches `document.documentElement.lang` on change.
  Cosmetic until a second locale ships.
- Agent LLM output (briefs, transcripts, recheck reasons) is model-generated
  and out of scope, as is API error prose.
